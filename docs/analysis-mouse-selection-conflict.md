# 滚轮滚动为何打断了原生拖选复制

分析对象：`src/tui/` 的全屏 TUI，引入滚轮滚动的那次改动（commit `decfc53`）。
现象：加了鼠标滚轮后，原本在终端里「按住左键拖动选中、松开即复制」的原生能力失效。

> **状态：方案 C 已实施。**
> 现在保留 `?1000h`，由程序自己实现选区：按下 → 拖动 → 松开即复制（copy-on-select，
> 与 opencode 一致），复制走 OSC 52 + 平台命令回退。同时滚轮被限制在对话流区域内生效。
> 本文保留作为「为什么原生拖选拿不回来」的原因记录；`SPH_MOUSE=0` 仍是「交还鼠标、
> 换取原生拖选」的退路。

## 一句话结论

这不是「滚轮处理函数把选中流程覆盖了」，而是**开启终端鼠标上报本身改变了鼠标事件的所有权**。
终端把鼠标变成协议数据流，通过 stdin 送给程序，于是「选中」这个由终端自己实现的功能再也
拿不到鼠标事件。滚轮只是我们**为了让上报有个正当理由才开的**，真正造成副作用的是上报本身——
而非解析滚轮的那几十行代码。

## 根因链（四层，自下而上）

| # | 机制 | 后果 |
|---|------|------|
| 1 | 进入 alt screen（`?1049h`） | 屏幕内容不属于 scrollback，终端自身的滚动能力整体失效：滚动条拖不动、Shift+PgUp 被吞、Ctrl+F 搜不到 |
| 2 | 于是程序必须自己接滚轮，只能开鼠标上报（`?1000h` + `?1006h`） | 终端把鼠标事件改为上报给程序，**不再自己处理任何鼠标交互**，其中就包括拖选 |
| 3 | 鼠标报文进 stdin，被我们的解析器消费 | 按键流里只有「滚轮能滚」是新增行为；左键按下/拖动/松开被解析成 `ignore` 后丢弃 |
| 4 | 我们**没有**实现应用内的选中/复制 | 被丢弃的选中意图没有任何替代实现 → 用户感知为「原来的功能没了」 |

第 1 层是第 2 层的原因，第 2 层是现象的原因，第 4 层决定现象是「失效」而不是「换了个实现」。

## 关键细节逐条对应代码

### 1. 为什么必须开上报

`src/tui/ansi.ts`：

```ts
altScreenOn: '\x1b[?1049h\x1b[2J\x1b[H',
mouseOn: '\x1b[?1000h\x1b[?1006h',
mouseOff: '\x1b[?1006l\x1b[?1000l',
```

关掉鼠标上报时，滚轮事件在 alt screen 里**根本到不了程序**——终端既不自己滚（没有 scrollback），
也不转发。所以「要滚轮」和「要原生拖选」在当前架构下是一道二选一。

代码里只开了两种模式，且是有意克制：

- `?1000h` 按键事件跟踪 —— 够收到滚轮（滚轮在协议里就是一个按键码），且不产生移动事件洪流；
- `?1006h` SGR 扩展坐标 —— 坐标以文本 `\x1b[<b;x;yM` 形式给出，避免老式 X10 的原始字节
  落进输入行变成乱码，同时不受 223 列坐标上限约束。

刻意**没开** `?1002h`（按住拖动时的移动事件）。注意：这一点**不改变结论**——选择功能归终端还是
归程序，由 `?1000h` 这一个开关决定，与是否订阅移动事件无关。不开 `?1002h` 只是少收一堆无用的
拖动报文，并不会把拖选还给终端。

### 2. 上报之后鼠标事件去了哪里

`src/tui/keys.ts` 的 SGR 分支：

```ts
const code = button & ~0b11100;              // 掩掉 Shift/Meta/Ctrl 与「拖动中」位
if (final === 'M' && (code === 64 || code === 65)) {
  return { kind: 'wheel', direction: code === 64 ? 'up' : 'down' };
}
return { kind: 'ignore' };                    // 左/中/右键与拖拽，显式忽略
```

`src/tui/app.ts`：

```ts
if (key.kind === 'ignore') return;            // dispatch 最前，直接丢弃
```

也就是说：左键的 press / drag / release 三个事件（`binary 0`、`32+0` 拖动中、release）都**确实
被完整收到并解析了**，然后被主动扔掉。滚轮路径（`64`/`65`）是这条上报通道里唯一被赋予语义的
事件，并且被 `handleScrollKey` 优先消费。

### 3. 为什么「丢弃」是必须的，不是可选的

`?1000h` 和 `?1006h` 是**两个独立的能力协商**，没有绑定关系。终端厂商可能支持按键上报但不支持
SGR 坐标扩展，此时报文退回老式 X10：

```
ESC [ M <Button+32> <Col+32> <Row+32>
```

`M` 后面跟的是 **3 个不含 `<` 的原始字节**，且多半落在可打印 ASCII 区间。若不专门吞掉，它们会被
当成用户输入写进输入行——表现出来就是「鼠标一动，输入框里冒出一串乱码」。`KeyParser.x10Remaining`
就是为此存在，并且必须跨 chunk 保持（chunk 边界与报文边界无关）。

所以 `keys.ts` 里那句注释「必须显式忽略而不是当成 unknown」是这个问题的同一条脉络：**协议字节
绝不能泄漏进用户的可编辑文本**。鼠标按键事件被丢弃，客观上也是这条原则的延伸。

### 4. 权宜方案与它的破绽

`app.ts` 的 `mouseEnabled()` 提供退路：`SPH_MOUSE=0`（也接受 `false`/`off`/`no`）关闭上报，拖选恢复，
代价是滚轮失效（`PgUp`/`PgDn` 仍可用）。`view.ts` 的提示行也随 `state.mouse` 同步改写，
避免提示与真实按键不一致。

这是「二选一开关」，不是修复。它的破绽在于**用户的习惯动作不是先读文档再拖选**：看到文字、顺手
选中、复制失败——第一反应是「这个终端坏了」，而不是「该设个环境变量」。把代价写进文档是必要的，
但不能替代把功能做出来。

## 可行的修复方向

各方案的成本与保真度递增：

### 方案 A：Shift 透传（成本最低，保真度中等）

大多数终端（含 Windows Terminal）在鼠标被上报时，约定**按住 `Shift` 拖动即强制本地选择**。这条路
已经零成本可用，文档里也写了。缺点是依赖用户养成习惯，且一旦按了 Shift，滚轮也会变成不带修饰位的
另一套按键码——需要在 `keys.ts` 里留意（掩码 `~0b11100` 已经能正确识别带修饰位的滚轮，这一点没
问题）。

### 方案 B：选中期间临时关闭上报（成本中等，保真度较高）

让程序显式进入「选择模式」：按下某个键（如 `Ctrl+S` 或 `F2`）时发 `\x1b[?1000l\x1b[?1006l`，
把鼠标交还终端；再按一次恢复上报。这本质上是把方案 A 的习惯依赖变成一个显式动作，好处是可以顺便
在提示行说明状态。缺点是要维护一个额外的模式状态，且关闭上报期间滚轮失效。

### 方案 C：应用内自行实现选中与复制（成本最高，保真度最高）

这才是「根本修复」，也是 vim/htop 之外那些现代 TUI（如部分 agent CLI）走的路：

1. **打开拖动移动事件**：`?1002h`（按住拖动时上报）或 `?1003h`（任何移动都上报，更贵）。
   这正是当前刻意没开的那一项——实现选中就必须开。
2. **在 `keys.ts` 里把 `binary 0`（左键）与 `binary 32`（拖动中）从 `ignore` 升级为有语义的事件**，
   带上 `x`/`y` 屏幕坐标（SGR 报文本来就给了）。
3. **维护一个选择区间**（起点行列、终点行列，SGR 坐标是 1 基、相对视口），在绘制时把选中区域
   用 `inverse` 渲染——`view.ts` 里已有 `inverse` 这个「选择态」语义约定，可直接复用。
4. **复制**需要跨平台方案：OSC 52（`\x1b]52;c;<base64>\x07`）在部分终端可用但有长度限制和安全
   顾虑；更稳的是复用仓库里已有的 `koffi` 原生绑定，按平台调用剪贴板 API（Windows 用 COM/`clip.exe`，
   macOS 用 `pbcopy`）。
5. **坐标与绘制必须对齐**：当前整帧绘制时每行从 `ESC[2K` 清行开始、不做行尾补齐（`view.ts` 文件头
   第 3 条注释），这对选择渲染是有利的——空尾不会污染复制内容；但折行由 `view.ts` 统一负责，
   所以「屏幕行 → 逻辑行 + 列偏移」的映射必须建立在折行结果之上，否则选中区间会错位。
6. **滚动时的选择一致性**：滚动会改变视口，需要在 `state.scroll` 变化时决定是**保留锚点并随内容
   移动**（更符合直觉，但要把屏幕行换算成内容行）还是**清空选择**（简单但打断用户）。

推荐路径：**A（已有，当作兜底）→ C**。B 只是把 A 的习惯依赖变成显式动作，收益有限，可作为 C 落地
前的过渡。若短期不做 C，至少应在提示行或首次进入时的提示里明确「拖选请按住 Shift」，把失败成本
从「以为坏了」降到「知道按钮在哪」。

## 结论

冲突的根因不在滚轮的处理逻辑，而在**能力开关**：`?1000h` 一旦开启，鼠标事件的所有权就从终端
转移到程序，终端侧的拖选随即停用；而程序侧只实现了滚轮一种语义，其余事件按防乱码原则被丢弃，
于是用户感知为「原功能失效」。要让两者共存，要么把选择权显式交还终端（Shift 或模式开关），
要么在程序内把选中与复制完整实现（`?1002h` + 选择区间渲染 + 剪贴板写入）。
