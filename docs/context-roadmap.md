# 上下文窗口管理能力评估

状态：待决策（评估完成，无新增项）
日期：2026-09-24
依据：对照清单逐项代码审计（compact.ts / prefix-tracker.ts / recap.ts / attachments.ts / spill / session fold）；部分结论复用 2026-09-24 模型网关优化审视的既得证据

背景清单：

- 自动截断、摘要压缩、滑动窗口；支持 RAG 上下文注入、历史消息分片；
- 区分系统提示词、用户消息、Agent 思考、工具返回的不同消息角色。

## 一、结论先行

**四个清单里最深入、最完整的一项——这就是 sph 的招牌能力**（README 首条特性即是）。自动截断、摘要压缩、角色区分不但已实现，深度全部超出清单字面；「滑动窗口」被一个更好的方案**有意替代**；「RAG 注入」是唯一字面缺失，但它的职责被四条按需注入通道覆盖，属于设计取舍而非缺口。**无建议新增项，无调优点**（上下文估算的优化空间在模型网关审视中已核查过：估算已锚定真实 usage）。

## 二、逐项判定

| 清单项 | 判定 | 证据 |
| --- | --- | --- |
| 自动截断 | ✅ 三处 | ① **spill**：超过阈值（默认 8KB）的工具结果整段落盘 `~/.sph/spill/<session>/`，上下文只留头尾预览 + 绝对路径；写盘失败保留原文——"spill 是优化，不能变成结果丢失的原因"（`loop.ts:1060-1065`）。② 单工具输出 32KB clip（`tools/types.ts:147`）。③ 老工具结果 **stub 化**（压缩第一层，头尾预览替换全文） |
| 摘要压缩 | ✅ 三层，深度超出清单 | 80% 水位触发（整数运算防 float 边界漂移）：**第一层** stub 工具结果 → **第二层** LLM 增量摘要（最近 4 轮原文不动；摘要 prompt 是精心设计的工程品——向接收者模型声明"你看不到被压缩段的工具输出，事实必须内联"、固定分段空段写 (none)、增量合并规则防"前序摘要永久存活/早期历史蒸发"、700 词上限；可走 `[aux]` 便宜端点；`/compact <指令>` 支持聚焦压缩）→ **第三层**机械折叠兜底（摘要调用失败也能继续工作）。压缩即换新会话（session fork），原会话只追加事件、发送投影逐字节不变；provider 判超窗（`ContextOverflowError`，跨协议措辞归一化识别）→ force 无条件瘦身 + 重试同一请求 |
| 滑动窗口 | ⚠️ 有意不用字面滑窗，目标达成且更优 | naive 滑窗 = 头部改写 = 每步提示词缓存全灭。sph 用「**stub 边界冻结** + 摘要即系列新起点」实现同一目的：上下文有界、请求前缀字节稳定、缓存跨步命中。`KEEP_RECENT_TURNS=4` 的原文窗口只增不滑（`stubFromSession` 冻结机制，`compact.ts:556-563` 注释详述了不冻结时"每加一轮前移一格、缓存从切点全灭"的教训） |
| RAG 上下文注入 | ❌ 无向量检索；✅ 等价注入通道已有 | RAG 的职责（把相关材料按需送进上下文）由四条**按需注入**通道覆盖：① skills 渐进披露（SKILL.md 触发才载入，不占常驻前缀）；② `@` 附件（文件内容内联进 user 消息、图片走 data URL、越界/二进制/超限都有可见占位）；③ 嵌套 AGENTS.md 触碰即注入（TouchMemory，措辞与 system 内项目指令一致）；④ 子代理 fan-out（上下文隔离式检索，报告回传主会话）。向量 RAG = 检索索引依赖，个人 runtime 无此场景；真需要时走 MCP 接外部检索服务，core 零工作量 |
| 历史消息分片 | ✅ 等价形态 | 分片以三种形式存在：① compaction 切分（摘要段 + 最近原文段，边界落盘为 compaction 事件）；② 子代理会话独立 JSONL——上下文天然按任务分片，父会话只收最终报告；③ spill 按结果分片落盘。**重启续接**：fold 只回带 goal / failures / planMode / tokensUsed / depth，不带全量历史也能恢复工作状态 |
| 角色区分 | ✅ 完整 | `ChatMessage`：system / user / assistant / tool 四角色 + `parts`（图片多模态）+ `thinking`/`thinkingSignature`（Anthropic 思考块带签名回放，官方 API 对含 tool_use 的消息强制）+ `reasoning` 项（Responses 协议 `encrypted_content` 跨步回传，否则丢思考状态）。会话层 message / event 双轨：todo、usage、compaction、plan_mode、prefix_change、cache_miss、subagent 等事件**不进消息流**，投影时各归各位 |

超出清单但值得记录的既有工程：

- **前缀稳定性是系统性设计**：prefix-tracker 按 tools → system → messages 三段逐段 hash 观测变更来源；cache_miss 事件留痕（含错位原因描述）；system prompt 一轮内冻结；日期等易变内容放尾部消息只追加。
- **注入时机工程化**：背景任务完成推送、转向消息（steering）、记忆触碰都在**步骤边界**注入，绝不打断进行中的 LLM 调用。
- **recap 与压缩分离**：recap（idle 自动生成的"讲到哪了"）永不改动会话——只读快照生成、只用于展示；复用主轮次前缀保缓存命中；三重闸门（轮次下限 + 空闲时长 + 有新轮次）+ 90s 重试退避防空转。

## 三、做不做

**无建议新增项。**

- **RAG / 向量检索**：不做。四条按需通道已覆盖职责；核心加检索索引违背"宁可少加"；外部检索服务经 MCP 即插即用（`call_timeout_ms` 上限也已放宽到 60s，检索类 server 友好）。
- **字面滑动窗口**：不做。现有方案在同一目标上严格优于滑窗（有界 + 缓存稳定），替换它纯属倒退。
- **优化**：模型网关审视已核查——估算锚定真实 usage 已实现，前缀 hash 增量化收益趋零，无新候选。

## 四、对标注脚

- 这份清单是**托管平台/框架型**产品的语境（RAG 管道、消息分片是 LangChain / Dify 类框架的词汇）。端侧 agent 的上下文管理目标不同：**保住提示词缓存 + 让 provider 超窗成为可恢复事件**——sph 在这两点上做到了清单未要求的深度。
- Pi：同样把上下文工程列为核心（progressive disclosure 替代 RAG、auto-compaction）；dsh 的 Trajectory 视图与 sph 的追加事件流同思路。三家在"不做 naive 滑窗"上结论一致。
